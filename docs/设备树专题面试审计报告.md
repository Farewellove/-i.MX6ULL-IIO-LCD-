# 2. 完整 DTS 源码（按设备分组，从内核源码树实际提取）

## 2.1 Sensor Keys — platform 设备（根节点下）

```dts
/* 自定义节点 */
sensor_collect {
    compatible = "my,sensor_collect";
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_gpioled
                 &pinctrl_key>;

    key-gpio = <&gpio1 18 GPIO_ACTIVE_LOW>;
    led-gpio = <&gpio1 3 GPIO_ACTIVE_HIGH>;

    status = "okay";
};
```

配套 pinctrl（均在 `&iomuxc` 下）：

```dts
pinctrl_gpioled: ledgrp {
    fsl,pins=<
        MX6UL_PAD_GPIO1_IO03__GPIO1_IO03 0x10b0
    >;
};

/*key why*/
pinctrl_key: keygrp {
    fsl,pins=<
        MX6UL_PAD_UART1_CTS_B__GPIO1_IO18 0xF080
    >;
};
```

**面试要点**:
- platform 设备节点挂在根节点下（不在任何总线内），由 `platform_driver` 通过 compatible 匹配
- 注意 GPIO 属性名是**单数** `key-gpio` / `led-gpio`，与驱动 `of_get_named_gpio(node, "key-gpio", 0)` 严格一致（见 §4.1）
- KEY0 用的是 `UART1_CTS_B` 这个 PAD 的 **GPIO 复用功能**，而非 UART 功能 — PAD 名与功能名的差异是 i.MX pinctrl 的典型写法

## 2.2 AP3216C — I2C1 设备

```dts
&i2c1 {
    clock-frequency = <100000>;
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_i2c1>;
    status = "okay";

    ap3216c@1e{
        compatible="sensor_collect,ap3216c";
        reg=<0x1e>;
        status="okay";
    };
};
```

总线 pinctrl（`&iomuxc` 下，复用 UART4 引脚为 I2C1）：

```dts
pinctrl_i2c1: i2c1grp {
    fsl,pins = <
        MX6UL_PAD_UART4_TX_DATA__I2C1_SCL 0x4001b8b0
        MX6UL_PAD_UART4_RX_DATA__I2C1_SDA 0x4001b8b0
    >;
};
```

**面试要点**:
- `@1e` 是**单元地址**（unit address），必须与 `reg` 第一个 cell 一致（DTC 编译期强校验）
- I2C 设备地址在 DTS 中由 `reg` 决定；`i2c_driver` 匹配 = compatible 匹配 + 地址无关（地址只用于创建 i2c_client）
- AP3216C 节点**没有自己的 pinctrl 属性** — 它不需要额外 GPIO，总线引脚复用由父节点 `&i2c1` 的 pinctrl 负责

## 2.3 GT911 — I2C2 设备（本项目 DTS 最复杂节点）

```dts
&i2c2 {
    clock-frequency = <100000>;
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_i2c2>;
    status = "okay";

    gt911@5d {
        compatible = "sensor_collect,gt911";
        reg = <0x5d>;
        pinctrl-names = "default";
        pinctrl-0 = <&ts_int_pin>, <&ts_reset_pin>;
        reset-gpios = <&gpio5 9 GPIO_ACTIVE_LOW>;
        interrupt-parent = <&gpio1>;
        interrupts = <9 IRQ_TYPE_EDGE_FALLING>;
        irq-gpios = <&gpio1 9 GPIO_ACTIVE_LOW>;
        status = "okay";
    };
};
```

配套 pinctrl — **跨两个 pin controller**（本项目核心知识点）：

```dts
/* INT → 普通域 &iomuxc */
&iomuxc {
    ts_int_pin: ts_int_pin_mux {
        fsl,pins = <
            MX6UL_PAD_GPIO1_IO09__GPIO1_IO09  0x79
        >;
    };
};

/* RST → SNVS 域 &iomuxc_snvs ★ 不能放在 &iomuxc 下 */
&iomuxc_snvs {
    ts_reset_pin: ts_reset_pin_mux {
        fsl,pins = <
            MX6ULL_PAD_SNVS_TAMPER9__GPIO5_IO09  0x79
        >;
    };
};
```

**面试要点**:
- `pinctrl-0` 引用**两个不同 pin controller 的 group**，逗号分隔即 phandle 列表，pinctrl 框架按 group 归属自动路由
- 节点同时有 `irq-gpios`（给驱动 gpiod_get 用）和 `interrupts`（标准节点级中断声明）双属性，详见 §5
- 与 i2c2 上共存的 `wm8960@1a`（音频）、`ov5640@3c`（摄像头）地址不同，互不干扰

## 2.4 ICM20608 — SPI3 设备

```dts
&ecspi3 {
    pinctrl-names = "default";
    cs-gpios = <&gpio1 20 GPIO_ACTIVE_LOW>; /* 软件片选 */
    pinctrl-0 = <&pinctrl_ecspi3>;
    fsl,spi-num-chipselects = <1>;
    status = "okay";

    /*自定义设备节点，连接到ecspi3总线上，地址为0*/
    icm20608@0 {      /*@后面的0表示spi芯片接在哪个硬件片选上*/
        compatible = "sensor_collect,icm20608";
        reg=<0>;
        spi-max-frequency = <8000000>; /* 8MHz */
        status = "okay";
    };
};
```

配套 pinctrl（`&iomuxc` 下）：

```dts
/*手动配置pin引脚，其中CS/SS通过软件片选*/
pinctrl_ecspi3:ecspi3grp{
    fsl,pins =<
    MX6UL_PAD_UART2_TX_DATA__GPIO1_IO20     0x10b0
    MX6UL_PAD_UART2_RX_DATA__ECSPI3_SCLK    0x10b1
    MX6UL_PAD_UART2_CTS_B__ECSPI3_MOSI      0x10b1
    MX6UL_PAD_UART2_RTS_B__ECSPI3_MISO      0x10b1
    >;
};
```

**面试要点**:
- SPI 节点的 `reg=<0>` 表示芯片挂在**第 0 个片选**上；`@0` 与之对应
- 本项目用 **GPIO 软件片选**（`cs-gpios`），所以 CS 引脚复用为 `GPIO1_IO20` 而非硬件 `ECSPI3_SS0`，由 SPI 框架自动控制 CS 电平
- `spi-max-frequency` 是 DTS 声明的速率**上限**（8MHz），驱动 `spi_setup()` 中实际配置 1MHz（icm20608.c:185）— 面试官可能追问两者关系（见 §6.1）

## 2.5 LCD — lcdif 控制器 + 7 寸 1024x600 时序

```dts
&lcdif {
    pinctrl-names = "default";
    pinctrl-0 = <&pinctrl_lcdif_dat
                 &pinctrl_lcdif_ctrl>;
    display = <&display0>;
    status = "okay";

    display0: display {
        bits-per-pixel = <32>;
        bus-width = <24>;

        display-timings {
            native-mode = <&timing0>;
            timing0: timing0 {
            clock-frequency = <51200000>;
            hactive = <1024>;
            vactive = <600>;
            hfront-porch = <160>;
            hback-porch = <140>;
            hsync-len = <20>;
            vback-porch = <20>;
            vfront-porch = <12>;
            vsync-len = <3>;

            hsync-active = <0>;
            vsync-active = <0>;
            de-active = <1>;
            pixelclk-active = <0>;
            };
        };
    };
};
```

pinctrl：`pinctrl_lcdif_dat`（LCD_DATA00~23 共 24 根数据线，全部 `0x79`）+ `pinctrl_lcdif_ctrl`（CLK/ENABLE/HSYNC/VSYNC 4 根控制线，全部 `0x79`）。

**面试要点**:
- `display-timings` + `native-mode` 是内核标准显示时序绑定，驱动 `simple-panel`/`mxsfb` 按此配置 LCDIF 寄存器
- 详细时序参数表见 [notes/LCD_1024x600_timing.md](../notes/LCD_1024x600_timing.md)

# 3. compatible ↔ of_match_table ↔ 驱动 三方对照表

| DTS 节点 | DTS compatible | 驱动 of_match_table | 驱动文件:行号 | 匹配方式 |
|---------|---------------|-------------------|-------------|---------|
| sensor_collect | `my,sensor_collect` | `my,sensor_collect` | sensor_driver.c:332 | platform: 根节点直接匹配 |
| ap3216c@1e | `sensor_collect,ap3216c` | `sensor_collect,ap3216c` | ap3216c.c:256 | I2C: i2c2 总线枚举子节点匹配 |
| gt911@5d | `sensor_collect,gt911` | `sensor_collect,gt911` | lcd.c:568 | I2C: i2c2 总线枚举子节点匹配 |
| icm20608@0 | `sensor_collect,icm20608` | `sensor_collect,icm20608` | icm20608.c:270 | SPI: ecspi3 总线枚举子节点匹配 |

**面试点 1**: 4 个 compatible 前缀**不统一** — 3 个 `sensor_collect,` + 1 个 `my,`。若被追问，诚实回答：`my,sensor_collect` 是项目早期第一个驱动（2026-04-09 首个提交），后续驱动统一改用 `sensor_collect,` 前缀，遗留了命名不一致。改进做法是统一前缀或改为 `alientek,` 风格。

**面试点 2**: 三种匹配机制的区别（高频面试题）:
- **platform_driver**: 设备节点挂在根节点/SoC 总线（`simple-bus`）下，内核启动时生成 platform_device，`of_match_table` 直接匹配
- **i2c_driver**: 节点挂在 `&i2cN` 下，I2C 总线驱动枚举子节点创建 i2c_client，client->addr 来自 `reg`，再按 of_match_table 匹配驱动
- **spi_driver**: 同 I2C 逻辑，`reg` 决定片选号而非地址

**面试点 3**: `MODULE_DEVICE_TABLE` 的作用 — 把 of_match_table 导出到 .modinfo 段，depmod/udev 据此自动加载模块（ap3216c.c:260-264 有注释）。没有它模块不会自动加载，但不影响手动 insmod。

# 4. GPIO / IRQ 属性 ↔ 驱动解析 API 对照表

## 4.1 新旧两套 API 并存（本项目特色，面试高频）

| DTS 属性 | 驱动解析代码 | API 风格 | 文件:行号 |
|---------|------------|---------|----------|
| `reset-gpios = <&gpio5 9 GPIO_ACTIVE_LOW>` | `devm_gpiod_get_optional(dev, "reset", GPIOD_OUT_LOW)` | descriptor 新 API | lcd.c:482 |
| `irq-gpios = <&gpio1 9 GPIO_ACTIVE_LOW>` | `devm_gpiod_get_optional(dev, "irq", GPIOD_IN)` | descriptor 新 API | lcd.c:495 |
| `key-gpio = <&gpio1 18 GPIO_ACTIVE_LOW>` | `of_get_named_gpio(node, "key-gpio", 0)` + `gpio_request()` | legacy 旧 API | sensor_driver.c:227,243 |
| `led-gpio = <&gpio1 3 GPIO_ACTIVE_HIGH>` | `of_get_named_gpio(node, "led-gpio", 0)` + `gpio_request()` | legacy 旧 API | sensor_driver.c:234,249 |

## 4.2 面试要点

**点 1 — 属性名必须严格一致**: 驱动解析的字符串与 DTS 属性名是**逐字节匹配**的。descriptor API 有约定规则：`gpiod_get(dev, "reset")` → 自动查找 `reset-gpios`（con_id + "-gpios"）；旧 API `of_get_named_gpio(node, "key-gpio", 0)` → 原样查找名为 `key-gpio` 的属性。

**点 2 — 单复数问题**: 内核标准绑定属性名是**复数** `xxx-gpios`。本项目 sensor_collect 节点用了**单数** `key-gpio`/`led-gpio`（旧教程风格，非标准），因为旧 API 没有自动加后缀的约定，属性名完全由调用者决定。如果将来迁移到 descriptor API（Q53 改进方案），DTS 属性名必须同步改为 `key-gpios`/`led-gpios`，否则 `devm_gpiod_get()` 找不到属性。这是本项目 DTS 的一个**已知不规范点**，面试被问到要能主动说出来。

**点 3 — GPIO_ACTIVE_LOW 只影响逻辑值**: `<&gpio1 3 GPIO_ACTIVE_HIGH>` 第三个 cell 是极性标志，只影响 gpiod 系列 API 的**逻辑值**（`gpiod_set_value`），不影响物理电平（`gpiod_set_raw_value`）。GT911 复位时序全程用 raw API 正是为了绕开这个翻转（lcd.c:147-155 注释）。LED 实际物理低电平点亮，DTS 却标 ACTIVE_HIGH 是因为驱动用旧 API `gpio_set_value()` 直接写物理值 + 手动取反 — 语义不严谨但功能正确。

**点 4 — GPIO 全局编号计算**: i.MX6ULL GPIO 全局编号 = `32 × (组号 - 1) + 引脚号`：

| 引脚 | 计算 | 全局编号 |
|------|------|---------|
| GPIO1_IO03 (LED) | 32×0+3 | 3 |
| GPIO1_IO09 (GT911 INT) | 32×0+9 | 9 |
| GPIO1_IO18 (KEY0) | 32×0+18 | 18 |
| GPIO1_IO20 (SPI CS) | 32×0+20 | 20 |
| GPIO5_IO09 (GT911 RST) | 32×4+9 | **137** |

（GT911 笔记中旧 API 测试代码 `gpio_request(137)` 即 GPIO5_IO09，可交叉印证）

# 5. interrupt-parent / interrupts 双 cell 解析（GT911 节点）

```dts
interrupt-parent = <&gpio1>;
interrupts = <9 IRQ_TYPE_EDGE_FALLING>;
```

| 部分 | 值 | 含义 |
|------|-----|------|
| `interrupt-parent` | `&gpio1` | 中断信号的控制器是 GPIO1（即 GPIO1 控制器自身的中断输出连到 GIC） |
| `interrupts` 第 1 个 cell | `9` | 在 interrupt-parent 上的中断编号 → GPIO1 的 9 号中断线 → 对应 GPIO1_IO09 引脚 |
| `interrupts` 第 2 个 cell | `IRQ_TYPE_EDGE_FALLING` = 2 | 下降沿触发 |
| 换算到 GIC | 32 + 9 = 41 | GIC 前 32 号是 SGI/PPI，GPIO1 组中断从 32 开始 |

**GT911 节点的特殊性 — 双属性并存**:
- `interrupts` 属性：标准中断绑定，声明节点有中断能力
- `irq-gpios` 属性：给驱动用的 GPIO 属性
- 驱动实际路径：`devm_gpiod_get_optional(dev, "irq")` → `gpiod_to_irq(irq_gpio)`（lcd.c:528）→ `devm_request_threaded_irq()`（lcd.c:532）
- 即**驱动实际用的是 gpiod_to_irq 路径**，`interrupts` 属性对 GT911 驱动只是形式上的标准声明。面试被问"驱动用的哪个属性"要答 irq-gpios。

**对比**: sensor_collect 节点**没有** `interrupt-parent`/`interrupts` 属性 — 按键中断由驱动在 probe 中 `gpio_to_irq(key_gpio)`（sensor_driver.c:274）动态完成，DTS 不需要声明中断。

# 6. 双 pin controller：iomuxc vs iomuxc_snvs（本项目最强面试点）

## 6.1 硬件划分

| Pin Controller | 物理地址 | 管辖引脚 | 对应 DTS 节点 |
|---------------|---------|---------|--------------|
| iomuxc | 0x020E0000 | GPIO1 ~ GPIO4 | `&iomuxc` |
| iomuxc_snvs | 0x02290000 | GPIO5 + BOOT_MODE0/1 | `&iomuxc_snvs` |

本项目全部 9 个 pinctrl group 的归属：

| group | 所属控制器 | 引脚 |
|-------|-----------|------|
| pinctrl_gpioled | &iomuxc | GPIO1_IO03 |
| pinctrl_key | &iomuxc | GPIO1_IO18 (UART1_CTS_B) |
| ts_int_pin | &iomuxc | GPIO1_IO09 |
| ts_reset_pin | **&iomuxc_snvs** ★ | SNVS_TAMPER9 → GPIO5_IO09 |
| pinctrl_ecspi3 | &iomuxc | GPIO1_IO20 + UART2×3 |
| pinctrl_lcdif_dat/ctrl | &iomuxc | LCD_DATA00~23 + CLK/EN/HS/VS |
| pinctrl_i2c1 | &iomuxc | UART4_TX/RX |
| pinctrl_i2c2 | &iomuxc | UART5_TX/RX |

## 6.2 静默无效问题（本项目踩坑，面试必讲）

把 SNVS 域引脚（如 `MX6ULL_PAD_SNVS_TAMPER9__GPIO5_IO09`）写在 `&iomuxc` 下，**DTC 编译不报错**，但 iomuxc 驱动不认识这个 PAD 编号，引脚复用静默无效 — debugfs 显示 `MUX UNCLAIMED`。完整排查链见 [notes/GT911_driver_bringup_summary.md](../notes/GT911_driver_bringup_summary.md) 第二章。

**判断一个 PAD 属于哪个域的规则**: 宏名前缀 `MX6UL_PAD_` → 普通域；`MX6ULL_PAD_SNVS_` / `MX6ULL_PAD_BOOT_MODE` → SNVS 域。（注意：`MX6UL_PAD_UART5_*` 是普通域，UART5 引脚≠GPIO5）

## 6.3 pinctrl 子系统工作流程（面试标准答案）

```
设备节点 pinctrl-names = "default" / pinctrl-0 = <&group1, &group2>
  → 设备 probe 前，pinctrl core 按 phandle 找到 group
    → group 内有 fsl,pins = <PAD宏 + 功能选择 | pad control 值>
      → 按 group 归属路由到对应 pin controller (iomuxc / iomuxc_snvs)
        → pin controller 驱动写 SW_MUX_CTL 寄存器（选功能）和 SW_PAD_CTL 寄存器（电气属性）
          → 引脚复用生效
```

同一个 PAD 不能被两个设备同时 claim（本项目第五个问题，见 §10）。

# 7. pad control 值解析（本项目用到的 4 个值）

i.MX6ULL `SW_PAD_CTL` 寄存器位域（面试按此口径回答）：

| 位 | 名称 | 含义 |
|----|------|------|
| bit0 | SRE | 压摆率：0=慢速，1=快速 |
| bit5:3 | DSE | 驱动能力：000=关闭，110=R0/6，111=R0/7（最大） |
| bit7:6 | SPEED | 带宽：00=50MHz，01=100MHz，10/11=200MHz |
| bit8 | ODE | 开漏输出 |
| bit9 | PKE | 上下拉使能 |
| bit10 | PUE | 上拉/下拉方向选择（配合 PUS） |
| bit15:14 | PUS | 上下拉阻值：00=100KΩ下拉，01=47KΩ上拉，10=100KΩ上拉，11=22KΩ上拉 |
| bit13 | HYS | 迟滞（施密特）使能 — 输入引脚防抖用 |
| bit30 | SION | 软件输入使能：输出模式下强制输入通路工作（I2C 必需） |

本项目实际取值：

| 值 | 使用位置 | 逐位解析 | 为什么这么配 |
|----|---------|---------|-------------|
| `0x79` | GT911 INT/RST、LCD 数据+控制线 | SRE=1 快压摆, DSE=111 最大驱动, SPEED=01 100MHz, PKE=0 无上下拉 | EVK 常用默认值；LCD 数据线需要快压摆+强驱动保证 51.2MHz 时序 |
| `0x10b0` | LED (GPIO1_IO03)、SPI 软件片选 (GPIO1_IO20) | SRE=0, DSE=110, SPEED=10 200MHz, PKE=1, PUE=0, PUS=00 → **100KΩ 下拉** | LED 复位期间保持确定电平；CS 下拉保证无效电平 |
| `0xF080` | KEY0 (GPIO1_IO18) | HYS=1 **迟滞使能**, SPEED=11 200MHz | 按键输入用施密特迟滞滤毛刺，是硬件防抖第一道 |
| `0x4001b8b0` | I2C1_SCL/SDA、I2C2_SCL/SDA | bit30 **SION=1** + PKE=1, PUE=1, PUS=10 **100KΩ 上拉** + 慢压摆 | I2C 开漏总线必须外部/内部上拉；SION 让输出模式下也能读回 SDA 电平判断 ACK/NACK |

> 注：逐位含义以 i.MX6ULL 参考手册 IOMUXC 章节为准，上表为本项目 DTS 实际取值 + 正点原子注释语义。

# 8. DTS 与驱动/文档的差异点（面试可能被追问的坑）

| # | 差异点 | 说明 | 面试应对 |
|---|--------|------|---------|
| 1 | `spi-max-frequency = <8000000>` vs 驱动实际 1MHz | DTS 是上限声明，实际速率由驱动 `spi_setup()` 决定并覆盖 | icm20608.c:185 实际配 1MHz（MODE_0, 8bit） |
| 2 | 审计报告称 "ICM20608 SPI3 CS0"，DTS 用软件片选 | CS0 指 `reg=<0>` 第 0 片选；实现上是 `cs-gpios` GPIO 软件片选而非硬件 SS 引脚 | SPI 框架根据 cs-gpios 自动拉 CS |
| 3 | sensor_collect 无 interrupts 属性 | 按键中断由驱动 `gpio_to_irq()` 动态获取，DTS 不声明 | 对比 GT911 的双属性写法（§5） |
| 4 | ap3216c/icm20608 节点无自己的 pinctrl | 不需要额外 GPIO；总线引脚复用由 `&i2c1`/`&ecspi3` 父节点负责 | 体现"pinctrl 归属在哪一层"的理解 |
| 5 | i2c2 总线上共存 wm8960@1a、ov5640@3c | 同一条总线多设备靠 7-bit 地址区分（0x5d/0x1a/0x3c 不冲突） | 车载终端项目遗留节点，非本项目设备 |
| 6 | `beep` 节点在 &iomuxc 下用 `MX6ULL_PAD_SNVS_TAMPER1__GPIO5_IO01` | 这是**反例**：GPIO5 引脚写在了 &iomuxc 下（静默无效），本项目 GT911 踩过的坑在 beep 节点重现 | 面试被问到能指出这是 SNVS 域引脚放错域，展示洞察力 |
| 7 | 根节点 `gpioled`/`key` 被注释禁用 | 与 sensor_collect 复用同一引脚 (GPIO1_IO03/IO18)，为避免 pinctrl 冲突被注释掉 | 这正是主审计报告 §7.3 "pinctrl 冲突" 的实际证据 |

# 9. 设备树专题面试题（15 道，补齐主报告空白）

## 9.1 DTS 语法与结构

**Q-DT1: DTS / DTB / DTC 三者的关系？**
> 答案: DTS 是设备树源码（人类可读）；DTC (device tree compiler) 把 DTS 编译成 DTB（扁平化二进制，bootloader 加载）；DTSI 是被 DTS `#include` 的公共头文件。编译命令 `make dtbs`；反编译 `dtc -I dtb -O dts`。本项目板级文件 imx6ull-alientek-emmc.dts include 了 imx6ull.dtsi（SoC 级公共定义）。

**Q-DT2: 设备树节点、属性、phandle 分别是什么？**
> 答案: 节点是设备的层次化描述（`gt911@5d { ... }`）；属性是键值对（`compatible = "..."`, `reg = <0x5d>`）；phandle 是节点间引用机制 — label（如 `ts_int_pin:`）编译后变成 32 位句柄，`pinctrl-0 = <&ts_int_pin>` 通过 phandle 引用。

**Q-DT3: `gt911@5d` 中的 `@5d` 是什么？能随便写吗？**
> 答案: 单元地址 (unit address)，必须与节点 `reg` 属性第一个 cell 一致，DTC 编译期强校验。I2C 设备即 7-bit 地址；SPI 设备即片选号（`icm20608@0` 的 0 是片选）。同一总线下的兄弟节点单元地址不能重复。

**Q-DT4: `status = "okay"` 的作用？**
> 答案: 节点使能开关。`okay`/`ok` 启用，`disabled` 禁用（节点存在但不实例化设备）。本项目 `&i2c1`/`&i2c2`/`&ecspi3` 都显式设了 okay。dtsi 中默认 disabled 的节点在板级 dts 里重新声明为 okay 是最常见用法（override 语法 `&节点名 { }`）。

## 9.2 匹配机制

**Q-DT5: 设备树节点如何匹配到驱动？分三种情况说明。**
> 答案: ① platform 设备：根节点/`simple-bus` 下节点 → platform_device → platform_driver 的 `of_match_table` 按 compatible 匹配（sensor_collect）；② I2C 设备：&i2cN 下子节点 → i2c_client（addr 来自 reg）→ i2c_driver of_match_table 匹配（ap3216c/gt911）；③ SPI 设备：同 I2C，reg 表示片选（icm20608）。匹配失败则设备无驱动，在 sysfs 可见但无 probe。

**Q-DT6: compatible 属性为什么要 "厂商,型号" 两段？**
> 答案: 约定命名空间，防止不同厂商同名设备冲突（内核文档 devicetree-spec）。字符串是链表，越靠前越具体，内核按顺序尝试匹配。本项目 `sensor_collect,gt911` 的 sensor_collect 实际是自定前缀（非注册厂商），改进可用 `alientek,` 风格。

**Q-DT7: `MODULE_DEVICE_TABLE(of, ...)` 的作用？本项目 4 个驱动都写了吗？**
> 答案: 把 of_match_table 导出到模块 .modinfo 段，depmod 生成 modules.alias，udev 据此在设备出现时自动 modprobe。没有它只影响自动加载，不影响手动 insmod。ap3216c.c:260-264 有注释说明。

## 9.3 GPIO 与中断

**Q-DT8: `gpios = <&gpio1 3 GPIO_ACTIVE_HIGH>` 三个 cell 分别是什么？**
> 答案: cell1 = 目标 GPIO 控制器 phandle；cell2 = 该控制器上的引脚编号（gpio1 的 3 号 = GPIO1_IO03，全局编号 32×(1-1)+3 = 3）；cell3 = 极性标志（ACTIVE_HIGH/ACTIVE_LOW）。cell 个数由 gpio-controller 节点的 `#gpio-cells` 决定（i.MX6ULL 为 2 个 cell：编号+极性）。

**Q-DT9: GPIO_ACTIVE_LOW 影响物理电平吗？**
> 答案: 不影响。它只翻转 gpiod 逻辑 API（`gpiod_set_value`）的语义；物理电平由 `gpiod_set_raw_value`/`gpiod_direction_output_raw` 控制。GT911 复位时序（lcd.c:161-194）全程 raw API 直接控制物理电平做地址选择，注释明确说明原因。

**Q-DT10: `interrupt-parent` + `interrupts` 两个 cell 怎么理解？以 GT911 为例。**
> 答案: 见 §5 完整解析。interrupt-parent 指定中断控制器（&gpio1），interrupts 第一个 cell 是该控制器上的中断线号（9 = GPIO1_IO09），第二个 cell 是触发类型（IRQ_TYPE_EDGE_FALLING）。GPIO 控制器中断输出到 GIC 的编号为 32+9=41。

**Q-DT11: 驱动里 `gpiod_to_irq()` 和 DTS 的 `interrupts` 属性是什么关系？**
> 答案: 两条独立路径，都能拿到中断号。GT911 走 gpiod_to_irq(irq_gpio)（lcd.c:528），从 irq-gpios 属性派生；interrupts 属性是标准节点级中断声明（此驱动未直接使用）。有些驱动用 `platform_get_irq()` 读 interrupts 属性。两种做法共存是常见现象。

## 9.4 pinctrl

**Q-DT12: 描述 i.MX6ULL 从设备节点到引脚复用生效的完整流程。**
> 答案: 见 §6.3 流程图。关键点: ① 设备 probe 前 pinctrl core 自动生效 pinctrl-0；② fsl,pins 的宏 `MX6UL_PAD_xxx__yyy` 同时编码了 PAD 编号和复用功能（mux mode）；③ 第二个值是 pad control（电气属性）；④ group 必须放在正确的 pin controller 下。

**Q-DT13: i.MX6ULL 有两个 pin controller，怎么区分一个引脚属于哪个？放错会怎样？**
> 答案: iomuxc (0x020E0000) 管 GPIO1~4；iomuxc_snvs (0x02290000) 管 GPIO5 + BOOT_MODE。宏名含 `SNVS_`/`BOOT_MODE` 的属于 SNVS 域。放错**静默无效** — DTC 不报错，debugfs 显示 MUX UNCLAIMED。本项目 GT911 RST (SNVS_TAMPER9) 就是踩了这个坑，详见 §6.2 和 GT911 笔记第二章。

**Q-DT14: 一个 PAD 能同时给两个设备用吗？pinctrl 冲突怎么排查？**
> 答案: 不能。第二个设备 claim 时报 `pin already requested`（本项目实际报错见 GT911 笔记第五个问题）。排查: `cat /sys/kernel/debug/pinctrl/20e0000.iomuxc/pinmux-pins | grep 引脚名` 看谁占用了。解决: 换 PAD、禁用旧设备、或去掉重复的 pinctrl-0 引用。本项目根节点下 gpioled/key 节点（原教程节点）因与 sensor_collect 抢 GPIO1_IO03/IO18 被注释禁用。

**Q-DT15: I2C 引脚的 pad control 值为什么特殊（0x4001b8b0）？**
> 答案: 两点: ① I2C 是开漏总线，需要上拉（PKE=1, PUE=1, PUS=10 → 100KΩ 上拉）；② bit30 SION (Software Input On) 强制输出模式下输入通路仍工作 — I2C 主机发送时必须读回 SDA 电平判断从机 ACK/NACK，没有 SION 读到的永远是 0。这是 i.MX 平台 I2C 引脚的经典配置。
